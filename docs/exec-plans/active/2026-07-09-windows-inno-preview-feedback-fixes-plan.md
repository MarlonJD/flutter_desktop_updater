# Windows Inno Preview Feedback Fixes Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix Windows Inno publishing for the `2.6.1-dev.0` release preparation so custom installer output names stay consistent across the Inno script, local artifact, `release.json`, `.desktop_updater_publish.json`, hooks, upload, and validation while keeping Inno artifacts compatible with `desktop_updater` `2.5.0` and newer runtimes.

**Architecture:** Add a small Inno output-name resolver that runs before `PublishLayout.create`, then pass the resolved base name into both the layout and the Inno packager. Keep the existing zip, DMG, and PKG paths unchanged. Keep the Windows Inno updater floor at `"2.5.0"` and add regression coverage so the `2.6.1-dev.0` publish path does not accidentally raise or lower that compatibility contract.

**Tech Stack:** Dart release CLI, Flutter unit tests, Inno Setup script metadata, schema-v3 `release.json`, repository validation ladder.

- Generated Windows Inno mode must use one resolved installer base name for `OutputBaseFilename`, the compiled `.exe`, `release.json artifact.url`, `.desktop_updater_publish.json artifact.path`, and hook environment artifact paths.
- Script Windows Inno mode must fail early with a clear `FormatException` if `windows.installer.outputBaseName` conflicts with a literal `OutputBaseFilename` in the `.iss` script.
- Script Windows Inno mode may use `windows.installer.outputBaseName` as the source of truth when the script uses preprocessor variables that the resolver cannot evaluate.
- Generated Inno descriptors must use `minimumUpdaterVersion: "2.5.0"` for `innoInstaller` artifacts.

## Problem Summary

Issue comment `#60` reports that `desktop_updater: 2.4.6-inno.0` successfully handles installer updates and staging cleanup, but release CLI output-name consistency still needs a fix for the `2.6.1-dev.0` publishing path.

- `windows.installer.outputBaseName` can produce a real `.exe` name that differs from the `artifact.url` generated by `PublishLayout`, and a custom `.iss` file can introduce a third `OutputBaseFilename`.
- `ReleasePublisher` currently emits `minimumUpdaterVersion: "2.5.0"` for `innoInstaller` artifacts. Keep that as the intended compatibility floor for `2.6.1-dev.0`, and add tests so it stays `2.5.0`.

test("reads literal OutputBaseFilename from script mode", () async {
  final root = await Directory.systemTemp.createTemp("inno_output_name_");
  addTearDown(() async {
    if (await root.exists()) {
      await root.delete(recursive: true);
    }
  });
  final script = File(path.join(root.path, "setup.iss"));
  await script.writeAsString("""
[Setup]
OutputBaseFilename=ScriptSetup
""");

  final name = await resolveInnoOutputBaseName(
    config: InnoPublishConfig(
      kind: "inno",
      mode: "script",
      script: script.path,
    ),
    appName: "Example",
    version: "2.4.6",
    platform: "windows",
  );

  expect(name, "ScriptSetup");
});

test("rejects configured outputBaseName that conflicts with script", () async {
  final root = await Directory.systemTemp.createTemp("inno_output_name_");
  addTearDown(() async {
    if (await root.exists()) {
      await root.delete(recursive: true);
    }
  });
  final script = File(path.join(root.path, "setup.iss"));
  await script.writeAsString("""
[Setup]
OutputBaseFilename=ScriptSetup
""");

  expect(
    () => resolveInnoOutputBaseName(
      config: InnoPublishConfig(
        kind: "inno",
        mode: "script",
        script: script.path,
        outputBaseName: "ConfigSetup",
      ),
      appName: "Example",
      version: "2.4.6",
      platform: "windows",
    ),
    throwsA(
      isA<FormatException>().having(
        (error) => error.message,
        "message",
        contains("windows.installer.outputBaseName does not match"),
      ),
    ),
  );
});
