# Migrating From 2.x To 3.0

Desktop Updater 3.0 is a breaking release. It keeps the schema-v3 signed
release format and the high-level controller, but removes caller-controlled
trust, target, diagnostics, and native scheduling paths. A 3.0 application
must prove the update identity before it asks a platform helper to mutate the
installed application.

## 1. Why This Is Breaking

The 3.0 boundary is intentionally smaller:

- metadata signatures and pinned public keys are mandatory;
- the app supplies an expected package identity and a durable recovery store;
- one zip-first session owns check, verify, and stage results;
- install is an explicit prepare/commit/cancel/query transaction;
- native adapters derive the running target proof from process context;
- helper diagnostics remain platform-owned, while application diagnostics are
  written through app-owned recorders and callbacks.

There is no compatibility scheduler, generated transaction ID, caller-supplied
signer/elevation policy, or raw staged-path install fallback in 3.0.

## 2. Preflight

Run the migrator with the source major stated explicitly. It never guesses the
source version:

```sh
dart run desktop_updater:migrate --from 2 --path .
dart run desktop_updater:migrate --from 2 --path . --apply
dart run desktop_updater:migrate --from 2 --path . --check
```

`--from 1` remains available for the historical 1.x-to-2.0 migration. The
tool only rewrites simple scalar constraints. Path, git, SDK, nested, and
ambiguous dependencies are report-only manual findings.

| Invocation | Dependency constraint | Result |
| --- | --- | --- |
| `--from 1` | supported `^1.x` | rewrite to `^2.0.0` |
| `--from 1` | exact `^2.0.0` | no-op |
| `--from 1` | other 2.x or any 3.x | mismatch, nonzero, no write |
| `--from 2` | any 1.x | mismatch, nonzero, no write |
| `--from 2` | supported `^2.x` | rewrite to `^3.0.0` |
| `--from 2` | simple 3.x | no-op |

Review every manual finding. The migrator does not create keys, package IDs,
stores, transaction IDs, target proofs, or native ABI code.

## 3. Keys, Package Identity, and Feeds

Deploy the app's Ed25519 public-key map before enabling 3.0 updates. The same
map must authenticate both `app-archive.json` and the selected `release.json`.
The descriptor `packageId` must equal the application-owned identity.

```dart
const trustedKeys = <String, String>{
  "stable-2026": "base64-raw-ed25519-public-key",
};

final controller = DesktopUpdaterController(
  appArchiveUrl: Uri.parse(
    "https://updates.example.com/app-archive.json",
  ),
  expectedPackageId: "com.example.app",
  trustedReleasePublicKeys: trustedKeys,
  recoveryStore: appRecoveryStore,
);
```

Publish signed archive and descriptor metadata. A 3.0 runtime rejects an
unsigned or unknown-key result before returning an update or downloading its
artifact. Preserve the signed 2.x channel until all installed applications
have the pinned-key bridge required by the feed policy.

## 4. Diagnostics Are App-Owned

Remove `diagnosticsLogPath` from controller and native-runtime configuration.
Use `UpdateDiagnosticsRecorder`, `onProblemReport`, telemetry, or an
application-owned file sink. Native helpers continue to write their fixed,
redacted platform sinks; an app cannot redirect them through an install
request.

```dart
final controller = DesktopUpdaterController(
  appArchiveUrl: updateUrl,
  expectedPackageId: "com.example.app",
  trustedReleasePublicKeys: trustedKeys,
  recoveryStore: appRecoveryStore,
  diagnosticsRecorder: appDiagnosticsRecorder,
  onProblemReport: appSupportReporter,
);
```

Do not pass a helper log path through a Flutter channel or native ABI.

## 5. Durable Transaction Identity

Generate a lowercase canonical UUIDv4 and persist it before `prepare`. Persist
the expected version, build, package, channel, stage-provenance digest, and
transaction ID together. Read the marker back and compare it field-for-field
before crossing the platform boundary.

The recovery-store write is not complete until durable replacement and a
subsequent exact readback succeed. On write, readback, or stage-binding
mismatch, make zero native install calls and retain the marker for diagnosis.

## 6. Flutter Before and After

The 2.x controller allowed optional trust and recovery inputs and exposed
compatibility install arguments. In 3.0 both constructors require:

- `expectedPackageId`;
- a non-empty `trustedReleasePublicKeys` map;
- an app-owned `UpdateRecoveryStore`.

`DesktopUpdater.restartApp()` is restart-only. It does not accept or install a
raw staged path.

For low-level zip-first use, keep one session and pass only its result into
staging:

```dart
final session = DesktopUpdater().createZipFirstUpdateSession(
  appArchiveUrl: updateUrl,
  currentVersion: currentVersion,
  expectedPackageId: "com.example.app",
  trustedReleasePublicKeys: trustedKeys,
  installationIdentity: stableInstallId,
);
final check = await session.checkForUpdate();
if (check != null) {
  final staged = await session.downloadVerifyAndStage(checkResult: check);
  // Persist the 3.0 marker, then use the controller/platform handoff.
}
```

Do not construct `UpdateCheckResult` or `UpdateStageResult` in application
code; their production constructors are library-private and owner-bound.

### Exact 2.x names removed in 3.0

These names are removed, not deprecated compatibility entry points. Replace every use before shipping a 3.0 application:

| Removed 2.x name | 3.0 direction |
| --- | --- |
| `allowUnsignedMacOSUpdates`, `allowUnsignedUpdates` | Remove the opt-out; use mandatory signed app-archive and descriptor metadata with `trustedReleasePublicKeys`. |
| `requireIndexSignature`, `requireDescriptorSignature` | Remove the toggles; native preview verification is mandatory and has no unsigned mode. |
| `diagnosticsLogPath` | Use app-owned `diagnosticsRecorder`, `onProblemReport`, or telemetry. |
| `downloadZipFirstUpdate` | Use one `createZipFirstUpdateSession()`, then `checkForUpdate()` and `downloadVerifyAndStage(...)`. |
| `installAndRelaunch`, `scheduleInstallAndRelaunch` | Use the explicit prepare/commit/cancel/query/recovery transaction lifecycle. |
| Legacy `DesktopUpdaterPlatform.installUpdate(...)` raw-stage fallback | Pass an owner-bound verified session/result through the explicit controller or platform handoff. |
| `desktop_updater_prepare_install_v2` | Treat the old export as a rejecting tombstone; compile consumers against the explicit ABI2 exports. |

The migration guide uses “removed” deliberately: 3.0 does not retain a compatibility shim for these surfaces.

## 7. Low-Level Native Lifecycle

Replace convenience calls such as `installAndRelaunch` and
`scheduleInstallAndRelaunch` with:

1. persist the transaction ID;
2. prepare the retained, verified stage;
3. persist the reservation locator/status;
4. commit only from the post-exit path;
5. query or resolve/recover on startup according to the platform.

Read-only query is safe for status display. A pending marker must not be
cleared merely because a transport call timed out.

## 8. macOS

Use the explicit Swift helper API:

```swift
let reservation = try helper.prepareInstall(
    verifiedRequest,
    transactionID: transactionID
)
try helper.commitAfterExit(reservation)
```

Keep `queryTransaction` and `recoverPendingInstall` for the macOS recovery
capability. Remove generated-ID prepare overloads, diagnostics paths, and
unsigned-install flags. Public macOS update artifacts remain Developer ID
signed, hardened, notarized, stapled, and Gatekeeper-valid for production
distribution.

## 9. Windows C and .NET ABI2

Compile 3.0 consumers against the new header and use only the explicit ABI2
exports:

```text
desktop_updater_prepare_install_abi2
desktop_updater_commit_after_exit_abi2
desktop_updater_cancel_reservation_abi2
desktop_updater_query_transaction_abi2
desktop_updater_resolve_pending_install_after_exit_abi2
```

Every ABI2 request, result, and status begins with `abi_version` and
`struct_size`. Consumers must initialize the complete prefix and release
owned result/status strings with the ABI2 free functions. A truncated or
ABI-1 prefix is rejected before later fields are read.

The installed 2.x `desktop_updater_prepare_install_v2` binary export remains
only as a deterministic rejecting tombstone. It is absent from the 3.0 public
header and must not be rebound to the ABI2 layout. The .NET wrapper likewise
exposes explicit `PrepareInstall`, `CommitAfterExit`, `CancelReservation`,
`QueryTransaction`, and `ResolvePendingInstallAfterExit` methods with ABI2
P/Invoke entry points. `ScheduleInstallAndRelaunch` and mutating direct
`RecoverPendingInstall` are removed.

## 10. Protected Windows Helper

The installer owns helper discovery, protected endpoint identity, sealed
policy, Authenticode publisher rules, and elevation strategy. NuGet/helper
assets are discovery inputs, not caller-controlled authority. The adapter
reloads authenticated staged metadata and derives target proof, signer policy,
and elevation policy before the helper boundary.

Do not copy a helper into a caller-selected protected directory or forward
signer thumbprints/elevation flags from Dart.

## 11. Signing Boundaries

Ed25519 signatures authenticate release metadata. They are distinct from:

- Apple Developer ID signing, notarization, and stapling;
- Windows Authenticode and installer policy;
- Linux package/repository trust;
- the helper's local endpoint and process authentication.

Configure all applicable trust layers. A valid Ed25519 descriptor does not
make an unsigned macOS bundle, untrusted Windows helper, or unapproved Linux
package channel production-ready.

Windows direct-ZIP installations created by 2.x may not have an installed
identity marker. For an exact per-user app root, the Windows helper may adopt a
genuinely missing marker from the canonical marker in the verified staged ZIP,
but only after it repeats signed descriptor, sealed-policy, and stage-provenance
authorization. It never overwrites a malformed or mismatched marker; those
roots still require a fresh installer. Machine-wide installs continue to
require their matching installer-owned uninstall record.

## 12. Linux Source-First CMake

Linux consumers build the native SDK from source. Use the installed CMake
package and the helper discovery variable supplied by the installer; do not
invent a prebuilt helper target or ABI package. Every prepare request includes
the explicit transaction ID, canonical install root, running executable proof,
package identity, stage provenance, and matching installed identity marker.

The legacy self-contained-bundle target proof and generated transaction ID are
removed. The Flutter plugin derives `/proc/self/exe` and ignores Dart-supplied
path substitutions that do not match the running process.

## 13. Trust and Failure Timing

The expected order is:

```text
signed feed -> signed descriptor -> package identity -> verified artifact
    -> retained stage/provenance -> durable app marker -> native prepare
    -> durable helper journal -> commit/recovery -> verified relaunch
```

Failure at any stage stops before the next trust boundary. In particular,
signature, package, store readback, stage, or target-proof failures must not
be reported as a successful handoff. Keep evidence labels literal:
`verified locally`, `not run`, `blocked`, `candidate-only`, or
`release pending`.

## 14. Persistence and Recovery

On startup, read the app-owned marker and authenticate the native status by
transaction ID. Windows uses read-only query for inspection and the atomic
`resolvePendingInstallAfterExit` mutation for startup recovery. macOS and Linux
retain authenticated query plus their public recovery operation. Clear the
marker only after terminal status and verified filesystem/relaunch handling.

Old 2.x durable markers and native journal readers remain readable. Do not
rewrite old bytes merely because a 3.0 process inspected them; mutate only as
part of an explicit authenticated recovery.

## 15. Unsigned 2.x Bridge

There is no 3.0 server-side switch that makes an unsigned installed 2.x app
safe. Ship a trusted 2.x update containing the pinned-key map, then publish
the signed 3.0 feed. Do not add a compatibility flag, accept unknown keys, or
silently fall back to an unsigned descriptor.

## 16. Verification Checklist

- [ ] `dart run desktop_updater:migrate --from 2 --path .` reviewed.
- [ ] `flutter analyze` and focused migration/API tests pass.
- [ ] `app-archive.json` and every selected `release.json` are signed.
- [ ] The app pins the active key map and expected package identity.
- [ ] The app-owned recovery store has durable write and exact readback.
- [ ] Every platform persists a canonical transaction ID before prepare.
- [ ] No removed diagnostics, scheduler, generated-ID, ABI-1, or direct Windows
      recovery names remain in production consumers.
- [ ] macOS artifacts satisfy Apple signing/notarization gates.
- [ ] Windows helper/policy assets are installer-owned and Authenticode-valid.
- [ ] Linux consumers build source-first and provision the identity marker.
- [ ] Local validation is complete; credentialed target-host evidence is
      separately labeled `not run` or `release pending` when unavailable.
- [ ] Only after the exact release HEAD is validated: change the package to
      `3.0.0` and publish through the approved release process.
