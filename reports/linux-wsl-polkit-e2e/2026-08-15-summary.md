## Failure interpretation

The installed action is visible to `pkaction` and has the expected policy:
`allow_any=no`, `allow_inactive=no`, `allow_active=auth_admin_keep`, with the
expected fixed helper path. The installed files are root-owned and match the
expected helper/caller/policy values.

The exact TTY capture and journal show that `sudo -v` authentication succeeded,
but `pkexec` received no polkit password prompt and was denied. A matching
`pkttyagent --process "$$"` probe and an internal-agent `pkcheck` probe both
returned `Not authorized`. During a live user shell, logind reported
`Active=yes` for `marlonjd`, but the WSL pseudo-TTY session had no seat. The
directly proven root cause is the polkit authorization denial before broker
start. The likely host-level cause is WSL2/logind/polkit subject or agent
classification for this seat-less TTY; that deeper distinction is recorded as
an inference, not overstated as a proven implementation defect.

Transaction IDs were not generated. The journal records only helper socket
names and nonces before `pkexec` denied the request. No durable query, backup,
prepared, journal, control, crash, or recovery artifact was reached.
